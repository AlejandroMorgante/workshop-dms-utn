# 02 · Amazon S3 y nuestro primer objeto

Al terminar vas a tener un bucket privado, un archivo de ejemplo y el destino
preparado para la futura tarea DMS. La explicación para clase está en
[la etapa 02 de la web](https://utn.almorgan.dev/etapa-02-s3.html).

## Qué vamos a crear

| Recurso o configuración | Para qué sirve |
| --- | --- |
| Bucket de propósito general | Guardar objetos en la misma región del laboratorio. |
| Nombre reservado por cuenta y región | Evitar que otra cuenta ocupe el nombre elegido. |
| Bloqueo de acceso público y ACLs deshabilitadas | Mantener acceso mediante políticas. |
| Cifrado SSE-S3 | Cifrar los objetos con claves administradas por S3. |
| Versionado | Conservar versiones al escribir sobre una misma clave. |
| Lifecycle | Eliminar versiones no actuales después de un día, para preparar el destino DMS. |
| Política HTTPS | Rechazar solicitudes de transporte inseguro. |

El stack es **`infra/02-s3/`**, con estado independiente. No consume outputs de
Aurora ni modifica su red: S3 es un servicio regional, no un recurso dentro de
nuestra subnet. Usamos **`us-east-1`**, perfil **`workshop`** y la misma cuenta de
la etapa 01. No se crean todavía tareas, roles ni endpoints de DMS.

El bucket no admite SSE-C. Usamos SSE-S3 y no necesitamos una clave KMS propia ni
Bucket Keys, que optimizan SSE-KMS. El alcance de este laboratorio no incluye
ABAC, logs de acceso a objetos ni una configuración de auditoría de producción.
La política del bucket pertenece a este stack; en la etapa 03, los permisos de
DMS se agregan a su rol IAM, sin reemplazar esta política desde otro estado.

## 1. Preparar y crear

Desde la raíz del repositorio:

```sh
aws sts get-caller-identity --profile workshop
```

Copiá `infra/02-s3/terraform.tfvars.example` como
`infra/02-s3/terraform.tfvars` y reemplazá `expected_account_id` con tu cuenta.
Revisá perfil y región; si cambiaste el nombre del perfil, reemplazalo también
en los comandos de esta guía. No copies el archivo de variables de Aurora:
contiene parámetros que este stack no usa.

```sh
terraform -chdir=infra/02-s3 init
terraform -chdir=infra/02-s3 plan
terraform -chdir=infra/02-s3 apply
```

Revisá el plan antes de confirmar. El nombre sigue este patrón:
`utn-dms-lake-<cuenta>-us-east-1-an`. El sufijo corresponde al namespace
`account-regional`. No hace falta buscar un nombre libre entre todas las cuentas.
Si ya tenés otro laboratorio con ese nombre en tu cuenta, elegí otro
`workshop_name` en las variables; no importes ni borres buckets ajenos al taller.

**Al habilitar versionado por primera vez, AWS recomienda esperar 15 minutos
antes de escribir objetos.** Aprovechá ese intervalo para recorrer la consola y
los conceptos del paso siguiente. No es necesario esperar para consultar la
configuración del bucket.

## 2. Reconocer el destino

```sh
terraform -chdir=infra/02-s3 output
```

En **S3 → General purpose buckets**, abrí el bucket que muestra `bucket_name`:

1. En **Properties**, ubicá región, versionado habilitado y cifrado SSE-S3.
2. En **Permissions**, revisá las cuatro opciones de bloqueo público y
   `Bucket owner enforced`. Las ACLs están deshabilitadas.
3. Leé la política: `DenyInsecureTransport` deniega HTTP. No otorga acceso público.
4. En **Objects**, el bucket está vacío. No creamos carpetas vacías.

Un **objeto** combina contenido y metadatos. Su **clave** es el nombre completo
dentro del bucket. `exploracion/tienda.json` es una clave; `exploracion/` es un
prefijo. La consola lo presenta como carpeta, pero no hay un directorio que
necesitemos crear antes de subir el archivo.

El output `dms_prefix` reserva el texto `dms` para el futuro endpoint. Un output
no crea una carpeta en S3. Mantenemos los archivos de exploración separados de
los datos que DMS escribirá bajo `dms/`.

## 3. Guardar el nombre en la terminal

**macOS o Linux:**

```sh
workshop_bucket=$(terraform -chdir=infra/02-s3 output -raw bucket_name)
```

**Windows · PowerShell:**

```powershell
$workshop_bucket = terraform -chdir=infra/02-s3 output -raw bucket_name
```

Los comandos restantes funcionan en ambas terminales con esa variable.
Si abrís otra terminal, volvé a definirla. Confirmá el destino antes de subir:

```sh
aws s3api head-bucket --bucket "$workshop_bucket" --profile workshop --region us-east-1
aws s3 ls "s3://$workshop_bucket/" --profile workshop --region us-east-1
```

`head-bucket` puede mostrar metadatos del bucket según la versión de CLI; debe
terminar sin error. El listado vacío es lo esperado en este momento.

## 4. Subir y explorar un archivo

Abrí [`data/tienda.json`](../data/tienda.json). Es un archivo ficticio de muestra;
no es una exportación de Aurora ni una salida de DMS.

Una vez transcurrido el intervalo de propagación del versionado:

```sh
aws s3 cp data/tienda.json "s3://$workshop_bucket/exploracion/tienda.json" --content-type application/json --profile workshop --region us-east-1
aws s3 ls "s3://$workshop_bucket/" --profile workshop --region us-east-1
aws s3 ls "s3://$workshop_bucket/exploracion/" --profile workshop --region us-east-1
```

El primer listado muestra el prefijo `exploracion/`; el segundo, el objeto
`tienda.json`. En la consola, entrá al objeto y buscá clave, tamaño, tipo de
contenido, cifrado y versión.

```sh
aws s3api head-object --bucket "$workshop_bucket" --key exploracion/tienda.json --profile workshop --region us-east-1 --query '{Bytes:ContentLength,Tipo:ContentType,Cifrado:ServerSideEncryption,Version:VersionId}'
aws s3 cp "s3://$workshop_bucket/exploracion/tienda.json" - --profile workshop --region us-east-1
```

Esperamos `application/json`, cifrado `AES256`, un `VersionId` y el contenido del
archivo. El guion final envía la descarga a la terminal. Que el objeto sea privado
no impide leerlo con tu identidad autorizada; una URL anónima no tiene ese permiso.

Para comparar prefijos con las carpetas de la consola:

```sh
aws s3api list-objects-v2 --bucket "$workshop_bucket" --prefix exploracion/ --profile workshop --region us-east-1 --query 'Contents[].{Clave:Key,Bytes:Size}'
```

Este comando devuelve la clave completa, incluida `exploracion/`.

## 5. Observar el versionado

Volvé a ejecutar **una vez** el mismo comando de carga del paso 4. Conserva el
contenido, pero genera otra versión del objeto. Compará:

```sh
aws s3 ls "s3://$workshop_bucket/exploracion/" --profile workshop --region us-east-1
aws s3api list-object-versions --bucket "$workshop_bucket" --prefix exploracion/tienda.json --profile workshop --region us-east-1 --query 'Versions[].{Clave:Key,Version:VersionId,Actual:IsLatest}'
```

El listado común muestra un objeto actual; el segundo permite ver las versiones.
En la consola, activá **Show versions**. La regla de lifecycle elimina versiones no actuales después de un día; no borra
la versión actual. La eliminación es asíncrona. El versionado de objetos no es CDC:
conserva versiones de un archivo, no eventos de filas PostgreSQL.

## 6. Dejar preparado el siguiente paso

```sh
terraform -chdir=infra/02-s3 output bucket_name
terraform -chdir=infra/02-s3 output bucket_arn
terraform -chdir=infra/02-s3 output dms_prefix
```

La etapa 03 usará esas salidas para configurar el rol y el endpoint S3 de DMS.
El prefijo `exploracion/` queda fuera de `dms/` para que la muestra JSON no se
mezcle con los futuros archivos Parquet. Conservá el estado de ambos stacks.

Al cerrar esta etapa deberías poder explicar:

- Qué diferencia a un bucket, una clave y un prefijo.
- Por qué una cuenta autorizada puede leer un objeto privado.
- Qué conserva S3 cuando subimos dos veces a la misma clave.
- Por qué guardar un archivo todavía no crea una tabla en Glue ni una consulta en Athena.

## Si algo falla

- **AccessDenied:** comprobá la cuenta y el perfil. La práctica necesita permisos
  de listado del bucket y sus versiones, lectura y escritura de objetos. La
  creación con Terraform requiere además administrar la configuración y política
  del bucket. `sts:GetCallerIdentity` no verifica esos permisos.
- **BucketAlreadyOwnedByYou:** verificá si existe un stack anterior y su estado;
  usá otro prefijo para un laboratorio separado.
- **NoSuchKey tras la primera carga:** verificá la clave exacta y el tiempo de
  propagación inicial del versionado. Esperá y repetí la lectura.
- **No aparece `dms/`:** es normal hasta que DMS escriba objetos con ese prefijo.
- **BucketNotEmpty al destruir:** aún quedan objetos, versiones o marcadores de
  borrado. Seguí el proceso de limpieza de abajo.

## Limpieza

Si continuás con DMS, conservá el bucket. Si terminaste:

1. Confirmá cuenta y nombre con el output `bucket_name`. Si ya existe una tarea
   DMS escribiendo aquí, detenela y eliminá primero su stack según su guía.
2. En la consola S3, seleccioná **solo el bucket de este laboratorio** y elegí
   **Empty**. Revisá el nombre y confirmá el vaciado. **Esto elimina de forma
   permanente todos sus objetos, versiones y marcadores de borrado.**
3. Esperá a que el vaciado termine. Luego:

```sh
terraform -chdir=infra/02-s3 plan -destroy
terraform -chdir=infra/02-s3 destroy
```

`force_destroy = false` evita que Terraform vacíe el bucket automáticamente.
`aws s3 rm --recursive` no alcanza para vaciar un bucket versionado: deja
versiones anteriores y marcadores de borrado. Usamos la consola para que el
participante revise el destino antes de eliminar todos los datos.

Los objetos y sus versiones generan consumo de almacenamiento; las solicitudes
pueden generar consumo adicional. Esta limpieza no elimina Aurora: si terminaste
el laboratorio completo, seguí también la limpieza de la etapa 01.
